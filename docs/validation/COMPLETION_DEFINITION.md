# 검증 완료의 정의

> WO-FCE-SAMPLE-VIABILITY-01 PHASE 6 정본. 트랙별 "검증 완료"는 여기서만 정의한다.

## 0. 왜 다시 정의하나

"4주 검증"은 캘린더 기준이었다. 그래서 **"3주 검증했다"는 거짓 진술이 가능했다** — 실제
유효 관측일은 트랙별로 14 / 5 / 1 / 7일이었다.

직전 WO가 "유효 관측일"로 바꿔 그 거짓을 걷어냈다. 그런데 유효 관측일도 충분조건이 아니었다.
폴리는 유효일을 다 채워도 정산 표본이 0이다. **며칠 봤는가가 아니라 몇 개를 채점했는가**로
말해야 한다.

## 1. 정의

```
트랙별 검증 완료 =
      유효 관측일   >= 28
  AND 채점 가능 표본 >= 30
  AND 표본이 포함한 시장 국면 >= 2
```

- 세 조건을 **모두** 만족해야 완료다.
- 하나라도 미달이면 **미달 항목을 명시한다.**
- **트랙별로 독립 판정한다.** 크립토가 완료됐다고 전체가 완료된 것이 아니다.

구현: `app/validation/sample_viability.py::validation_completion`
회귀: `tests/test_sample_viability.py`

### 각 조건이 막는 것

| 조건 | 없으면 생기는 거짓말 |
| --- | --- |
| 유효 관측일 ≥ 28 | "3주 검증했다" — 실제로는 정지 구간이 절반이었다 |
| 채점 가능 표본 ≥ 30 | "28일 관측 완료" — 정산이 0건이라 채점된 게 없다 |
| 시장 국면 ≥ 2 | "승률 60%" — 상승장 한 국면에서만 얻은 수치다 |

30은 도메인 불변("정직한 표본")의 N<30 판정 유보 기준과 같은 수다. 게이트를 통과시키려고
이 수를 낮추지 않는다.

> ⚠️ **재검토 중 (WO-FCE-SAMPLE-RATE-01 Phase 3).** 실측 결과 30건은 게이트 축 2(성과 우위,
> CI 비겹침)가 요구하는 판정을 지탱하지 못한다 — 그 방법으로 30건에서 우위를 주장하려면
> **40%p 우위**가 필요하고, 15%p 우위를 잡으려면 **팔당 283건**이 필요하다.
> 30과 CI 비겹침은 서로 모순되며, 바뀌어야 할 쪽은 게이트가 아니다.
> 선택지와 재산정 근거: [`REQUIRED_SAMPLE.md`](REQUIRED_SAMPLE.md). **채택 전까지 30을 유지한다** —
> 재검토 중이라는 이유로 기준을 미리 내리지 않는다.

## 2. 국면 라벨은 진입 시점에 기록한다

국면(`uptrend` / `downtrend` / `quiet_range` / `volatile_range`)은 **진입 시점에** 원장에
남긴다(`entry_evidence.market_regime`). 사후에 다시 라벨링하면 룩어헤드다.

라벨이 없는 트랙은 조건 3을 **미달로 둔다.** `available=False` 를 "충족"으로 처리하면 완료
정의가 무의미해진다. 폴리는 현재 여기 해당하며, 라벨 배선 전까지 미달로 표시된다.

## 3. 대시보드 표기

`/validation` 화면과 `GET /api/system/paper/diagnosis` 의 `sample_viability.completion` 이
같은 문자열을 낸다.

```
크립토 페이퍼   유효일 14/28  ·  표본 4/30  ·  국면 1/2     [미달: 채점 가능 표본, 시장 국면]
폴리마켓 페이퍼 유효일  7/28  ·  표본 0/30  ·  국면 -        [구조적 차단]
```

- 세 칸을 **같은 크기로** 둔다. 유효일만 크게 표시하면 "거의 다 됐다"는 착시가 생긴다.
- **가장 뒤처진 조건이 그 트랙의 상태다** (`laggard`). 진행률을 평균 내지 않는다 — 평균은
  유효일이 표본 0을 가려버린다.
- 구조적 차단 트랙은 미달 목록 대신 `[구조적 차단]` 으로 표기한다. 시간이 해결하지 않는
  상태를 "조금 느린 것"처럼 보이게 하지 않는다.

## 3-2. 검증 창 앵커 (WO-FCE-WINDOW-ANCHOR-01)

### 계수 범위는 생애 누적이 아니라 창 기준이다

이전까지 `effective_days` 는 **트랙의 역사상 모든 유효일 개수**였고, 표본 SQL 8종 전부 시각
조건이 없었다. 그래서 재시작을 실행해도 스코어보드만 0으로 돌아가고 검증 카운터는 어제 값
그대로 남았다 — **재시작이 검증 경로에 도달하지 않았다.**

이제 트랙마다 **창 앵커**가 있다. 정본: `validation_windows` 테이블 ·
`app/validation/window_anchor.py`.

| 축 | 필터 |
|---|---|
| 유효 관측일 | `observation_coverage.day >= anchor_day` |
| 진입·채점 표본 (8쿼리) | `t >= anchored_at` |
| 검증 시계 | 앵커 이후 **최초 유효일**부터 시작 |

**창은 필터지 삭제가 아니다.** 앵커 이전 행은 하나도 지우지 않으며, 계수에서 빠진 건수는
`window_excluded` 로 조회 가능하다 — "0건"과 "창 밖 40건"은 다른 상태다.

**앵커가 없으면 현행 동작(생애 누적)과 완전히 동일하다.** 지금 운영 DB 에는 앵커가 없으므로
배포 직후 숫자는 배포 전과 같다.

### 창 상태 3종 — `D+28에 아무 일도 일어나지 않는다`

목표 유효일을 넘겨도 카운터는 계속 올라갔고, **그 상태를 표현할 이름이 없었다.** 이름이 없으면
화면은 계속 "진행 중"으로 보이고, 트랙은 미달 상태에 무기한 머문다.

| 상태 | 조건 | 표시 |
|---|---|---|
| `running` | 목표일 이내, 조건 미충족 | 진행 중 |
| `complete` | 3조건 전부 충족 | 조건 충족(완료) |
| `overrun` | **목표 유효일 경과, 조건 미달** | 목표일 경과·조건 미달 |

유효일은 목표값에서 **상한 처리하지 않는다** — `31/28 (목표일 경과)`. `28/28` 에서 멈춰 보이면
창이 이미 지났다는 사실이 화면에서 사라진다.

### 한 줄 형식

```
[창 2회차 · 앵커 2026-08-17] 크립토 페이퍼  유효일 31/28 (목표일 경과)  ·  표본 12/30  ·  국면 1/2     [목표일 경과 · 미달: 채점 가능 표본, 시장 국면]
```

회차·앵커를 병기하지 않으면 어느 창의 숫자인지 알 수 없다.

재시작 절차와 확인 항목: [`docs/RESTART_RUNBOOK.md`](../RESTART_RUNBOOK.md).

## 4. 진술 규칙

문서·대시보드·보고 어디서든 검증 진행을 말할 때:

- ✕ "3주 검증 중"
- ✕ "거의 다 됐다"
- ✕ "D+14 — 절반 왔다" (표본을 말하지 않았다)
- ○ "크립토 유효 관측일 14/28, 채점 가능 표본 4/30 — 표본 부족"
- ○ "폴리 유효 관측일 7/28, 채점 가능 표본 0/30 — 구조적 차단"

## 5. 금지

- 세 조건 중 일부만 보고 "완료"라고 쓰기
- 목표치(28 / 30 / 2)를 통과시키려고 낮추기
- 국면 라벨이 없는 것을 "충족"으로 처리하기
- 캘린더 일수·주 단위로 진행을 말하기
- N<30 인 상태에서 승률·수익률을 계산해 보고하기
