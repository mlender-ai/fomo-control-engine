# 고래 알림 승격 조건 (Whale Alert Promotion)

> WO-FCE-WHALE-ALERT-DEMOTE-01 Phase 4 정본.
> **이 문서는 결과를 보기 전에 커밋됐다.** 강등한 신호가 푸시로 되돌아오는 조건을
> 되돌아오고 싶어진 시점에 정하면, 그건 조건이 아니라 사후 합리화다.
> **배선하지 않는다.** 이 문서는 조건만 정의한다. 승격은 자동으로 일어나지 않는다(C4).

## 0. 지금 상태 — 강등

`whale_entry` 는 `app/notify/delivery_gate.py::DEMOTED_RULES` 에 있다. 텔레그램 개별 푸시
**0건**이다. 그 외에는 전부 그대로다:

| 경로 | 상태 |
|---|---|
| 온체인 체결 수집 (`app/onchain/`) | **유지** — 손대지 않았다(C2) |
| DB 원장 저장 | **유지** |
| 진단 API 조회 (`/api/paper/diagnosis` → `whale_observations`) | **유지 + 확장** — 미발송 건과 사유를 조회 가능(C3) |
| 일 1회 요약 1줄 | **신설** — 24h 집계만, 개별 건·지갑명 없음 |
| 텔레그램 개별 푸시 | **차단** |

강등의 근거는 빈도가 아니라 **검증 부재**다. 빈도를 조이는 접근(쿨다운·배치 창)은 선행 WO에서
이미 실패했다 — 배치 identity 에 체결 ID·건수가 들어가 `state_key` 가 매번 새로 생성됐고,
따라서 쿨다운이 **구조적으로 한 번도 적용된 적이 없었다.** 같은 지갑에서 6건이 같은 분에
도착한 것은 파라미터 문제가 아니었다.

## 1. 승격 조건 (전부 미정 — 사용자 결정)

아래 표의 임계값은 **하나도 확정되지 않았다.** 제안값은 논의의 출발점이며, 승인 전까지
승격은 일어나지 않는다.

| # | 축 | 종류 | 제안값 | 왜 이 축인가 |
|---|---|---|---|---|
| 1 | **사후 채점 표본 N** | 측정 | ≥ 30 (**미정 — 사용자 결정**) | N<30 에서는 승률 CI 폭이 결론을 못 낸다. 현행 관측 표본은 아래 §2 참조 |
| 2 | **승률 하한** | 측정 | 단독 수치 금지 — CI 하한 기준 (**미정 — 사용자 결정**) | 점추정 승률은 표본이 작을수록 낙관적으로 보인다. 이 저장소의 판정 규칙은 CI 비겹침이다 |
| 3 | **누적 R 하한** | 측정 | > 0 (**미정 — 사용자 결정**) | 승률이 높아도 누적 R 이 음수면 신호가 아니라 잡음이다. 두 축은 함께 봐야 한다 |
| 4 | **지갑당 발송 상한** | 정책 | 미정 (**사용자 결정**) | 승격해도 상한이 없으면 같은 스팸이 재발한다. 강등의 직접 원인이 무제한이었다 |
| 5 | **주기당 발송 상한** | 정책 | 미정 (**사용자 결정**) | 4와 같은 이유. 지갑별 상한만으로는 지갑 수가 늘면 총량이 다시 열린다 |
| 6 | **인적 승인** | 사람 | 1~5 전부 충족해도 사용자 명시 승인이 최종 조건 | 자동 승격 금지(C4). 미검증 신호를 푸시로 되돌리는 것은 코드가 정하지 않는다 |

### 축 2·3 — 왜 승률과 누적 R 을 따로 두는가

승률만 보면 작은 이익을 자주 내고 큰 손실을 가끔 내는 신호가 통과한다. 누적 R 만 보면
소수의 큰 적중이 다수의 실패를 가리는 신호가 통과한다. 둘 다 걸어야 둘 다 막힌다.

### 축 4·5 — 상한 없는 승격은 강등 이전으로 되돌아가는 것이다

승격 조건을 통과했다는 것은 "신호가 유효하다"는 뜻이지 "무제한 발송해도 된다"는 뜻이 아니다.
발송 상한은 신호 품질과 **독립적인** 별개의 결정이다.

## 2. 현재 관측 표본 — 결론을 낼 수 없다

WO 가 제시한 실측(2026-08-08 기준): **승률 20.0% · N=5 · 누적 -3.00R**.

**N=5 는 표본 부족이다.** 이 숫자로는 "고래 신호가 나쁘다"도 말할 수 없다 — 승률 20%의 95%
신뢰구간은 대략 0.5%~72% 로, 동전 던지기와 우수한 신호를 모두 포함한다. 강등의 근거는
"나쁘다는 증거"가 아니라 **"좋다는 증거가 없다"** 이며, 이 둘은 다르다.

일 1회 요약 1줄에도 같은 이유로 N<30 이면 "표본 부족"을 병기한다(C6).

## 3. 승격 절차 (배선 없음)

1. §1 의 6축 임계를 **사용자가 확정**하고 이 문서에 기록한다.
2. 확정된 임계에 대해 실측을 산출한다. 표본은 사후 채점 원장에서 나온다 — 수집은 이미
   계속되고 있으므로 강등 기간에도 표본은 쌓인다.
3. 전 축 충족 시 **사용자에게 보고**한다. 코드가 스스로 판정해 발송을 재개하지 않는다.
4. 사용자 승인 후에야 `DEMOTED_RULES` 에서 `whale_entry` 를 빼고 상한을 배선하는 별도 WO 를
   연다.

> 3→4 사이에 자동 경로는 없다. 그것이 C4 다.

## 4. 미해결 (사용자 결정 대기)

| # | 질문 | 왜 지금 못 정하나 |
|---|---|---|
| D1 | 표본 N 하한을 30 으로 할 것인가 | 검증 완료 정의(`COMPLETION_DEFINITION.md`)와 같은 30 을 쓸지, 고래 신호에는 다른 수를 쓸지 |
| D2 | 승률을 CI 하한으로 걸 것인가, 벤치마크 대비 우위로 걸 것인가 | 고래 신호의 대조군이 무엇인지 정해지지 않았다 — "고래 진입 직후 매수" 대 "무작위 시점 매수"의 비교 설계가 없다 |
| D3 | 지갑당·주기당 상한의 구체 수 | 발송 총량 예산이 정해진 적이 없다. 상한을 정하려면 "하루 몇 통까지 받을 것인가"가 먼저다 |
| D4 | 강등 유지 기간의 하한을 둘 것인가 | 조건만 통과하면 언제든 승격 가능하게 할지, 최소 관측 기간을 둘지 |

## 승격 0명의 원인 확정 (WO-FCE-SMART-MONEY-01 4-1 · 2026-08-20)

4주째 승격 0명의 원인은 **표본 부족이 아니었다.**

```
채점 표본        265건 / 39지갑 · 축적 7.6건/일
N>=30 도달       2지갑 (39건 · 34건)
게이트 통과      0명
전체 승률        134/265 = 50.6%   CI [44.2, 56.6]
```

병목은 둘이다:

1. **코호트 회전** — N≥30 에 도달한 2개 지갑이 **현재 추적 20지갑에 없다.** 성과 기반
   재선발(D4)이 표본 축적을 리셋한다. 현재 추적군 최대 N=16
2. **`ci_low >= 55.0`** — N=39 지갑은 표본 요건을 충족하고 `ci_low 35.9` 에서 탈락했다

그리고 그 임계는 **N=30 에서 승률 73.3%**, N=265 에서도 61.1% 를 요구한다. 실측 50.6% 가
유지되면 **어떤 N 에서도 통과하지 못하며**, N 이 커질수록 CI 가 50.6% 주변으로 좁혀져
55% 에서 멀어진다(N=1000 → CI 상한 53.8%).

> **푸시 복귀 조건을 "표본 30건 달성"으로 두면 영구 미결이 된다.** 표본은 달성되지만
> 승률이 임계를 넘지 못한다. 복귀 조건은 **우위 유무**로 서술해야 하며, 현재 측정값은
> 풀 수준에서 **우위 없음**이다.

`whale_entry` 푸시 강등(PR #11)은 **유지가 옳다.** 이 문서의 미결 항목 중 "언제 되살리는가"는
**측정이 답을 줬다 — 아직 아니다.**

정본: [`SMART_MONEY_01.md`](SMART_MONEY_01.md)

## 알림 조건 확정 (WO-FCE-WHALE-FOLLOW-01 5-4 · 2026-08-25)

### 배선하지 않았다

WO §0 이 조건을 걸었다 — 승격 통과자 0명이면 5-4 를 착수하지 않는다. **실측 통과자 0명**
이므로 알림 rule 을 만들지 않았다. `test_follow_track_is_not_wired` 가 미배선을 고정한다.

### 위 결론의 "영구 미결" 판정을 정정한다

이 문서는 풀 승률 50.6% 를 근거로 "표본은 달성되지만 승률이 임계를 넘지 못한다 · 어떤 N
에서도 통과하지 못한다"로 닫혔다. **풀 수준에서는 맞고, 개별 지갑 판정으로는 과했다.**

2026-08-25 실측에서 `0x10f1d8…202f` 가 N=37 · 승률 **64.9%** 다. 그 승률이 유지되면
**N=94 에서 CI 하한 55.3%로 통과한다**(추가 57건 · 현 축적 속도로 약 14일). 도달 불가가
아니라 **아직 도달하지 않았다.**

나머지 두 지갑(51.3% · 50.0%)에 대해서는 원 판정이 유효하다 — N=1,500 까지 불가다.

### 복귀 조건 — 서술을 고친다

"표본 30건 달성"은 여전히 잘못된 조건이다(원 판정 유지). 그러나 "우위 없음"도 지금은
정확하지 않다. **복귀 조건은 현행 승격 기준의 통과 그 자체다** — 28일 · N≥30 · CI 하한 55%.
그 기준이 실효적으로 요구하는 것:

| 승률 | CI 하한 55% 도달에 필요한 N |
| --- | --- |
| 58.0% | 967 |
| 62.5% | 156 |
| 65.0% | 81 |
| 75.0% | 30 |

즉 **N≥30 조건은 승률 75% 를 함축하고, 현실적 표본에서는 승률 62.5% 이상이 실효 기준이다.**
기준을 낮추자는 제안이 아니라, 기준이 무엇을 요구하는지 적어두는 것이다.

### 배선 시 적용할 조건 (결과 전 고정)

| 항목 | 확정 |
| --- | --- |
| rule id | `whale_follow_entry` — `whale_entry`(강등 유지)와 별개다 |
| 관문 | `notify/delivery_gate` 통합 관문 경유. 우회 경로 없음 |
| 발송 대상 | 승격 고래 **이고** `directional` 추정 지갑의 `opened`/`closed` 만 |
| 상한 | 지갑당 시간당 상한 · 주기당 총 상한. 처음부터 넣는다(C6) |
| `state_key` | **배치 내용에 비의존.** 배치마다 새 키가 생겨 쿨다운이 무력화된 것이 `WHALE-ALERT-DEMOTE-01` 스팸 사고의 기전이었다 |
| 본문 필수 | 고래 식별 · 유형 추정과 신뢰도 · 표본 N 과 CI 하한 · 진입가·방향·무효화가 · 체결→진입 지연 · **실주문이 아닌 엔진 가상 거래 기록임** |
| 정숙 시간 | 제거됨 (2026-09-04) |

정본: [`WHALE_FOLLOW.md`](WHALE_FOLLOW.md)

## 관찰 알림과 승격 알림의 구분 (Phase 6-3 · 2026-08-25)

배선했다. 위 절의 "배선하지 않았다"는 Phase 5 상태이고, Phase 6 가 §0 조건을 대체했다
(근거: [`WHALE_FOLLOW.md`](WHALE_FOLLOW.md) — 승격 기준을 페이퍼의 전제로 쓰는 것이 순환).

### rule 이 셋이 됐다

| rule id | 무엇의 알림인가 | 상태 |
| --- | --- | --- |
| `whale_entry` | **고래 체결 자체** | **강등 유지** |
| `whale_follow_entry` | **엔진이 그 체결을 보고 가상 진입을 했다** | **신설·허용** |
| (승격 알림) | 승격 고래 추종 진입 | 같은 rule, `qualification=promotion` 라벨 |

`whale_entry` 를 되살리지 않았다. 그것은 미검증 고래의 체결을 그대로 흘려보내는 것이었다.
`whale_follow_entry` 는 **우리 행동**의 알림이다 — 엔진이 무엇을 했는지는 알 가치가 있다.

### 스팸 기전은 구조적으로 막았다

강등 사유는 빈도가 아니라 기전이었다 — `identity` 에 체결 ID·건수가 들어가 배치마다 새
`state_key` 가 생겼고, 쿨다운이 조회하는 키가 매번 달라 상한이 존재하지 않았다.

```python
def alert_identity(*, address, symbol, direction, phase) -> str:
    return f"{address.lower()}:{symbol.upper()}:{direction}:{phase}"
```

**네 축뿐이다.** 체결 ID·건수·시각·금액이 없다. 같은 지갑이 같은 심볼에 같은 방향으로 다시
진입하면 키가 같으므로 쿨다운이 실제로 걸린다. `test_identity_does_not_depend_on_batch_content`
와 `test_state_key_is_stable_across_repeated_entries` 가 고정한다.

그리고 쿨다운에 더해 **명시적 상한을 처음부터** 넣었다:

| 상한 | 값 |
| --- | --- |
| 지갑당 시간당 | 3건 |
| 실행당 총량 | 5건 |

상한은 **원장에서 계산한다.** 별도 상태 저장소를 두면 그것이 드리프트하고, 드리프트한
상태는 상한이 없는 것과 같다 — 그것이 정확히 지난번 사고였다.

### 본문 필수 항목

| 항목 | 예 |
| --- | --- |
| 고래 식별 · 유형 추정 · 신뢰도 | `고래 0x10f1…202f · unclassified 추정` |
| **미검증 라벨** | `⚠️ 미검증 관찰 자격 진입 (승격 아님)` |
| 표본 N · CI 하한 | `표본 N=38 · CI 하한 50.0%` |
| 진입가 · 방향 · 무효화가 | `BTCUSDT long · 진입 100 · 무효화 97` |
| 체결→진입 지연 | `체결→진입 12.0분` |
| 실주문 아님 | `실주문이 아닌 엔진 가상 거래 기록입니다.` |

승격 자격 진입은 첫 줄이 `승격 고래 추종 진입` 으로 바뀌고 `미검증` 문구가 빠진다. 두
자격이 같은 문면을 쓰면 구분이 사라진다.

### 우회 0건

발송 모듈에 `TelegramSender`·`send_telegram`·`httpx`·`requests` 가 없다. 후보만 만들고
워커가 기존 `evaluate_scout_setups` → `delivery_gate.evaluate_rule` 로 넘긴다. **새 발송
경로를 만들지 않는 것이 우회 0건의 형태다** — 관문이 둘이면 그중 하나는 반드시 잊힌다.

`opened`/`closed` 만 발송한다. 후보·관측·거부는 조회 대상이다.

## 추종 알림 문구 단순화 (WO-FCE-WHALE-FOLLOW-02 7-3 · 2026-08-25)

`whale_follow_entry` rule 본문이 바뀌었다. **강등된 `whale_entry` 와는 여전히 다른 rule 이고
발송 상한도 그대로다** — 바뀐 것은 문구뿐이다.

### 문제 — 라벨이 정보를 주지 못했다

Phase 6 본문은 모든 건이 똑같이 찍혔다:

```
⚠️ 미검증 관찰 자격 진입 (승격 아님)
표본 N=39 · CI 하한 35.9%
```

`미검증`·`승격 아님`은 **모든 건에 붙는 상수**라 건별 판단에 쓸모가 없었고, CI 하한은
자격 판정에서 빠진 값이라 왜 이 지갑을 따라갔는지 설명하지 못했다.


가르는 값이고, Phase 6 은 그것을 본문에 적지 않아 −1.83 USDT 청산이 왜 났는지 알림만
보고는 알 수 없었다.

### 청산 알림에 결과를 붙였다

```

```

진입과 청산이 짝으로 보여야 한다. `identity` 는 지갑·심볼·방향·**단계**를 쓰므로
`opened`/`closed` 가 서로를 삼키지 않고, `payload.pair_key` 가 둘을 잇는다.

### 미측정과 0% 를 구분한다

이탈이 없으면 `이탈 미측정`이라고 적는다. `0.00%` 로 적으면 "고래와 같은 값에 잡았다"는
뜻이 되는데, 그것은 측정하지 못한 것과 정반대의 주장이다.
