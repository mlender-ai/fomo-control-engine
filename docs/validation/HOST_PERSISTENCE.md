## 0. 문제

호스트(맥) 절전으로 02:00~05:00 KST 구간이 반복해서 비었다. **코드로 해결할 수 없다.**

| --- | --- | --- |
| `docs/ObservationIntegrity.md` §5 | 2026-07-15~08-05 소급 | 12시간 19분 / **8일** (24/7 트랙 기준) |

두 값은 창이 달라서 다르다. 비교할 때는 반드시 같은 창끼리 본다.

## 1. 왜 US 트랙만 특히 아픈가

```
US 정규장 (UTC)     13:30 ├──────────────────────────┤ 20:00   (6.5시간)
절전 구간 (UTC)                        17:00 ├────────┤ 20:00   (3시간)
```

절전 구간은 US 정규장의 **마지막 3시간, 즉 세션의 46%** 를 덮는다. 유효 관측일 임계는
커버리지 90% 이므로, **절전이 발생한 날의 US 세션은 통째로 유실일이 된다.** 부분 손실이
아니라 그날 하나가 없어지는 것이다.

KR 정규장(00:00~06:30 UTC)은 이 구간과 **겹치지 않는다.** KR 커버리지 저하를 절전 탓으로
돌리는 것은 오귀인이다 (`tests/test_coverage_axes.py::test_kr_session_cannot_be_explained_by_host_sleep`).

## 2. US 표본 회복 예상치

절전 발생일 비율을 `p` 라 하면 US 실현 속도는 `1 - p` 로 깎인다. 남은 유효일 `R` 을 채우는
데 걸리는 거래일은 `R / (1 - p)` 다.

실측 `p`:

- 소급 창(07-15~08-05, 거래일 16일 중 절전 8일) → `p ≈ 0.50`
- 운영 잡 창(최근 30일, 10일) → `p ≈ 0.33`

US 는 유효 관측일 1/28 이므로 남은 유효일 `R = 27`:

| 안 | 절전 후 `p` | 27 유효일 소요 거래일 | 현 상태 대비 단축 |
| --- | --- | --- | --- |
| A · B · C (절전 제거) | 0 | **27 거래일** | — |
| D (현 상태 유지) | 0.33 | 약 40 거래일 | +13 거래일 |
| D (현 상태 유지) | 0.50 | 약 54 거래일 | +27 거래일 |

> **절전을 제거하면 US 검증이 13~27 거래일 빨라진다.** 이것이 판단 근거다. 위 계산은 절전이
> 유일한 유실 원인이라고 가정한 상한이며, 다른 결함이 남아 있으면 단축 폭은 줄어든다.

## 3. 선택지 비교

| 안 | 내용 | 확인해야 할 것 | 비용 | 리스크 |
| --- | --- | --- | --- | --- |
| **A** | `caffeinate -dimsu` 상시 실행 | 노트북 전원 연결 유지 필요 · 발열 · **재부팅 시 자동 복구 여부** | 0원 | 재부팅 후 사람이 다시 실행해야 하면 같은 사고가 재발한다 |
| **B** | 시스템 설정에서 절전 해제 | A와 동일 + **설정 영속성**(OS 업데이트가 되돌리지 않는가) | 0원 | 배터리 구동 시 정책이 다를 수 있다 |
| **C** | 소형 VPS/클라우드 이전 | **실측 리소스 기반 사양**(§4) · 월 비용 · 이전 공수 · 시크릿 관리 · 네트워크 지연이 수집에 미치는 영향 | 월 비용 발생 | 이전 중 관측 중단 → 검증 시계 추가 유실. Toss 인증이 IP·기기에 묶여 있으면 재인증 필요 |
| **D** | 현 상태 유지 + 유실 명시 | 없음 | 0원 | US 표본이 계속 깎인다 (§2) |

A·B 는 `caffeinate` 가 살아 있는지를 **외부에서** 확인할 수 있어야 한다. 감시가 대상 안에
살면 함께 죽는다(AGENTS.md 도메인 불변). 현재 진단 API의 "수동 조치 필요" 배지가 그 역할을
하며, 절전 손실이 0이 되면 배지가 사라지는 것으로 조치 성공을 확인한다.

## 4. C 안 검토 시 — 사양은 실측으로 산정한다

**추측하지 않는다.** 다음을 돌려 실제 사용량을 잰 뒤 사양을 고른다.

```bash
FCE_SAMPLES=360 FCE_INTERVAL=10 scripts/local/measure-resources.sh   # 1시간 측정
```

출력: CPU 평균·최대(코어 합산), RSS 평균·최대, 네트워크 수신/송신, DB 크기.
원자료는 `logs/resource-usage.jsonl` 에 남는다.

사양 산정은 **최대치 기준 + 여유**로 한다. 평균 기준으로 잡으면 수집 피크에서 스로틀링이
걸리고, 그건 다시 커버리지 미달로 나타난다.

| 실측 항목 | VPS 사양 반영 |
| --- | --- |
| CPU 최대 | vCPU 수 (최대치 / 100% 올림 + 1) |
| RSS 최대 | 메모리 (최대치 × 2) |
| DB 크기 증가율 | 디스크 (현재 크기 + 검증 기간 증가분 × 3) |
| 네트워크 수신/시간 | 대역폭·트래픽 한도 확인 |

## 5. 임시 조치 (결정 전까지)

선택과 무관하게 **지금** 적용한다. 호스트 이전은 시간이 걸리고, 그 사이에도 US 표본은 깎인다.

```bash
scripts/local/check-sleep-guard.sh --apply
```

이 스크립트가 하는 일:

```bash
sudo pmset -a sleep 0 disksleep 0 standby 0 powernap 0   # AC 전원 기준 유휴 절전 해제
nohup caffeinate -dimsu &                                # wake lock (중복 실행 방지 포함)
```

- 배터리 구동 시 `Low Power Sleep` 이 별도로 걸리므로 **전원 상시 연결**이 필요하다.
- 클램셸(덮개 닫고 사용)이면 외부 전원 + 디스플레이가 있어야 한다.

### 자가 점검이 붙어 있다

**재부팅 후에도 유지되는지 반드시 확인한다.** 자동 복구가 안 되면 "적용됐다"고 말할 수
없고, 그 경우 사고는 반드시 재발한다. 확인은 사람 기억이 아니라 코드가 한다 —
`app/worker/sleep_guard.py` 가 매 진단마다 `pmset` 을 읽어 미적용이면
`manual_actions` 에 `sleep_guard_off` 를 올린다.

```bash
scripts/local/check-sleep-guard.sh           # 종료 코드 0=보호 중 / 1=미적용 / 2=판정 불가
curl -s localhost:8875/api/system/paper/diagnosis | python3 -m json.tool | grep -A 8 sleep_guard
```

재부팅 후 자동 복구가 안 되면 A 는 "적용됐다"고 말할 수 없다 — 그 경우 사고는 반드시
재발한다. 진단 API 의 `manual_actions` 가 절전 손실을 계속 보고하는지로 검증한다.

```bash
curl -s localhost:8875/api/system/paper/diagnosis | python3 -m json.tool | grep -A 12 manual_actions
```

## 매달림은 절전과 무관하다 (WO-FCE-LIVENESS-VERDICT-01)

절전 대책은 **US 정규장 후반 유실**을 겨눈 것이고, 그 구간은 02:00~05:00 KST 다.
그러나 하트비트 정체는 그 밖에서도 난다.

| 관측 시각 (KST, 2026-08-13) | 절전 구간(02:00~05:00)인가 |
|---|---|
| 03:21 | 예 |
| 04:20 | 예 |
| **15:21** | **아니오** |
| **16:20** | **아니오** |

**15:21·16:20 은 절전 구간이 아니다.** 그러므로 **절전 대책만으로는 해결되지 않는다** —
워커 잡 하나가 타임아웃 그물을 빠져나가 매달리는 별도 원인이 있다.

두 손실을 같은 이름으로 부르면 대책도 섞인다. 이 문서의 선택지(A~D)는 **절전 손실**에 대한
것이고, 매달림은 `WO-FCE-WORKER-HANG-02` 소관이다.

> 호스트 지속성을 해결해도 매달림은 남는다. 재시작 전에 둘 다 닫아야 새 창의 유효 관측일이
> 무엇 때문에 깎였는지 알 수 있다.
