# 알림 전달 구조 (Alert Delivery)

> WO-FCE-ALERT-SILENCE-01 정본. 관련: [`ALERT_SILENCE.md`](ALERT_SILENCE.md) · `docs/WorkerHangEvidence.md`

---

## 1. 무엇이 반복됐나

```
sync_positions ── 진입 알림 · 정기 펄스 · 구조 알림 · 무효화 경보
```

**단일 실패점이었다.** 이 잡이 450초 타임아웃으로 죽으면 알림 전체가 같이 죽었다.

| 날짜 | 침묵 | 기전 |
| --- | --- | --- |
| 9/1 | **15시간** | `sync_positions` 450초 타임아웃 3연속 |
| 이번 | **8시간 43분** | 같은 형태 |

`ENGINE-LIVENESS-01` D1 이 훅 격리로 **한 훅의 예외**를 막았고, `27b6e11` 이 **감지**와
화면을 고쳤다. **그러나 결합 자체는 남아 있었다** — 훅이 아무리 격리돼 있어도 **부모 잡이
취소되면 뒤쪽 훅은 시작조차 못 한다.**

---

## 2. 알림은 독립 잡이다 (3-1)

```
sync_positions   ── sync_and_analyze · detect_closures · paper_engine
deliver_alerts   ── evaluate_lifecycle · evaluate_alerts · evaluate_structure_context
                    · evaluate_performance_alerts · periodic_pulse · daily_summary
```

같은 주기로 돌되 **부모가 없다.** 동기화 결과는 `_last_sync_payload` 에 저장만 하고
알림 잡이 그것을 읽는다.

### 낡았으면 낡았다고 알린다

동기화가 죽어도 알림은 멈추지 않는다. 대신 페이로드에 낡음이 실린다:

```json
{"sync_stale": true, "sync_age_seconds": 10800,
 "sync_stale_note": "포지션 동기화가 180분째 갱신되지 않았다 — 아래 값은 그 시점 기준이다"}
```

**침묵보다 낡은 값이 낫다.** 침묵하면 동기화가 죽었다는 사실을 알릴 경로까지 사라진다.

### 진입·청산은 한 번만 소비한다

낡은 페이로드를 매 틱 다시 읽으면 같은 진입이 반복 판정된다. 쿨다운이 막아 주긴 하지만
거기 기대지 않고 `_consume_lifecycle_payload()` 로 비운다.

## 3. 훅이 부모 예산을 나눠 쓴다 (3-3)

훅마다 자기 예산이 있어도 **부모 잡의 타임아웃이 전체를 덮는다.** 훅 5개가 각자 450초를
받아도 부모가 450초면 첫 훅 하나가 그것을 다 먹는다.

```python
_HOOK_SHARES = {"sync_positions": 3, "deliver_alerts": 6}
hook_budget = max(min(parent_budget, interval), parent_budget // share)
```

> **타임아웃을 올리지 않는다**(C4). **나누는 것**이므로 모든 값이 작아진다. 느린 훅 하나가
> 잘리고 뒤쪽 훅은 살아남는다. 450초를 900초로 늘리면 죽는 시점만 미뤄진다.

`_HOOK_SHARES` 가 실제 훅 수와 어긋나면 예산이 다시 한 훅에 쏠린다 —
`test_hook_share_counts_match_the_actual_hooks` 가 그것을 고정한다.

## 4. 침묵 감지 — 외부 데드맨 (3-2)

### 왜 워커 밖인가

```
sync_positions 사망 → 모든 알림 정지 → 사망 알림도 정지(원래 강등)
                                     → 아무도 모른다
```

> **감시자가 감시 대상 안에 살면 침묵이 스스로를 은폐한다.**

그래서 판정을 `scripts/local/deadman.sh` 로 옮겼다 — 이미 워커 **밖**에 있고 앱 코드를
import 하지 않는다.

| 계층 | 무엇을 보나 |
| --- | --- |
| `liveness.json` | **잡 상태** — 하트비트 갱신 |
| `alert_delivery.json` | **발송 이력** — 마지막으로 실제 전달된 시각 |

**둘은 다른 것을 잰다.** 잡이 "정상"인데 알림이 0건인 구간이 실제로 있었다.

워커는 **기록만** 한다. 판정도 발송도 하지 않는다 —
`test_worker_writes_a_delivery_marker_but_does_not_judge` 가 그것을 고정한다.
발송 **성공** 시에만 기록한다. 실패를 성공으로 적으면 침묵 감지가 영영 안 울린다.

### 강등을 되돌리지 않는다 (C1)

생존·사망 신호는 사용자 지시(2026-08-16)대로 **그대로 강등돼 있다.** 침묵 알림은
**다른 신호**다:

| | 생존 알림(강등 유지) | 침묵 알림(신설) |
| --- | --- | --- |
| 보는 것 | 잡 상태 | **발송 이력** |
| 발화 시점 | 하트비트가 낡을 때 | **알림이 0건일 때만** |
| 발송기 | `send_telegram`(`DEADMAN_PUSH` 게이트) | `send_telegram_direct`(게이트 없음) |

정상 동작 중에는 **절대 울리지 않는다.**

### 정숙 시간에도 발화한다 (D3 결정)

```
정숙 시간   01:00 ~ 08:00 KST
침묵 구간   22:42 ~ 07:25
```

**정숙 시간이 진짜 침묵을 정상 침묵으로 위장한다.** 밤에 죽으면 아침 08:30 리포트까지
아무도 모른다. 그래서 침묵 감지는 정숙 시간을 무시하고, 대신 **하루 1회 상한**으로
스팸을 막는다(C6).

### 모르는 것을 침묵으로 단정하지 않는다

발송 이력 파일이 없으면 판정하지 않는다(`silence_age=-1`). 배포 직후나 알림이 한 번도
나간 적 없는 상태와 진짜 침묵은 다른 사건이다.

### 설정

```bash
FCE_ALERT_SILENCE_LIMIT_SECONDS=14400    # 4시간 — 이보다 오래 0건이면 발화
FCE_ALERT_SILENCE_REMIND_SECONDS=86400   # 하루 1회 상한 (C6)
FCE_ALERT_DELIVERY_PATH=../logs/alert_delivery.json
```

## 5. 실측으로 확인한 것

컨테이너에서 데드맨을 직접 돌려 세 가지를 확인했다:

| 조건 | 결과 |
| --- | --- |
| 하트비트 정상 · 알림 9시간 0건 | **침묵 알림 발화** |
| 같은 조건 · 상한 이내 재실행 | `침묵 지속 540분 — 하루 1회 상한으로 미발송` |
| 알림이 방금 나감 | **오탐 0건** |
| **워커도 죽은 상태** | 사망 알림은 강등 기록, **침묵 알림은 발화** ← 이 WO 의 핵심 |

## 6. 아직 산출하지 않은 것

**호스트 재기동이 선행이다.** 이 컨테이너에는 운영 워커가 없다.

| 항목 | 필요한 것 |
| --- | --- |
| 알림 공백 최대 구간 (24시간) | 운영 관측 |
| `sync_positions` 강제 종료 후 알림 생존 | 운영 호스트 |
| **450초를 먹는 훅 특정** (3-3 항목 1·2) | `job-trace.jsonl` · `loop-lag.jsonl` |
| 침묵 감지 오탐 이력 | 24시간 관측 |
| 잡 실행률 전후 | 재기동 전후 대조 |

> **3-3 은 절반만 했다.** 훅별 예산 분할은 코드로 넣었지만 **어느 훅이 450초를 먹는지는
> 특정하지 못했다** — 그것은 운영 트레이스가 있어야 한다. 예산 분할은 "하나가 전부를
> 먹는 것"을 막을 뿐 **느린 훅을 빠르게 만들지 않는다.**
