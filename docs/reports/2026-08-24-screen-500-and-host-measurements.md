## 1. 화면 500 — 500이 아니었다

증상: `/engine?tab=stocks` 가 `API request failed: 500`,
콘솔 `:8876/api/stock-paper/dashboard:1 → 500`.

**실제로는 백엔드가 응답을 못 하고 행에 걸렸고**(60초 타임아웃) 프론트가 그것을 500 으로
변환한 것이다. 독립된 두 결함이 겹쳐 있었다.

### 결함 A — 읽기 경로가 연결 단계에서 쓰기 락을 요구했다

```python
db/sqlite_utils.py  configure_sqlite_connection()
    connection.execute("PRAGMA busy_timeout=5000")
    connection.execute("PRAGMA auto_vacuum=INCREMENTAL")   ← 매 연결
```

기존 주석은 "기존 DB 에는 무해 no-op" 이라고 적혀 있었다. **무해하지 않다.**
이 pragma 는 DB 헤더에 쓰므로 **쓰기 락을 요구**하고, 긴 쓰기 트랜잭션(페이퍼 엔진)이 도는
동안 `busy_timeout` 5초를 넘겨 `database is locked` 를 던진다. 그 예외가
**쿼리 실행 전에 연결을 죽여** 읽기 엔드포인트까지 전부 죽었다.

그리고 이 DB 는 **이미 `auto_vacuum=2`** 였다 — 아무것도 바꾸지 않으면서 락만 요구했다.

**수리**: 먼저 읽어서 이미 INCREMENTAL 이면 쓰기를 건너뛴다(운영의 모든 경우).
바꿔야 할 때도 실패를 삼킨다 — 파일 크기 최적화 설정 하나 때문에 연결이 죽지 않는다.

### 결함 B — 관측 이벤트 표가 리텐션 대상이 아니었다

```
stock_paper_events              25,299,849행
  KR / reason=session_closed    25,287,541   ← 2026-08-14 하루에 폭주
  현재 유입                     15행/일       ← 폭주는 멈춘 상태
```

`store.dashboard()` 의 사유 집계가 `event_type` 으로 필터하는데 기존 인덱스
`(market, reason, observed_at)` 에 그 칼럼이 없어 **2,530만 행을 테이블에서 읽었다** — 45.3초.
그리고 `stock_paper_events` 는 리텐션 정책에 **없었다.**

| 조치 | 결과 |
| --- | --- |
| 마이그레이션 `0038` 커버링 인덱스 `(market, reason, event_type)` | 45.3s → 7.0s (`COVERING INDEX`) |
| 행 수 상한 리텐션(기본 20만) + 삭제 예산(200만/실행) | 25,299,849 → **200,000행** |

**날짜 창이 아니라 행 수 상한**으로 잡았다 — 폭주가 하루에 몰리므로 날짜 창은 그날이 창 안에
있는 동안 아무것도 못 막고, 벗어나면 한꺼번에 2,500만 행을 지운다. 둘 다 나쁘다.
**삭제 예산**을 둔 이유는 한 트랜잭션에 2,500만 행을 지우면 WAL 이 폭증하고 쓰기 락을 길게
잡아 **이번 장애와 같은 형태로 API 를 다시 내리기** 때문이다(실측 13회 · 회당 4~33초).


> **따라서 "267종 진입 0" 은 현재 코드에서 성립하지 않는다.** 실적 무데이터 심볼은

> 그것은 실적 공급원과 무관한 별개 항목이다.
>
> 리포트를 고치지는 않았다 — 그것은 `ASSET-CLASS-01` 소관이고, 술어 자체의 측정
> (`_earnings_clear` 는 실제로 무데이터에서 불통과다)은 정확하다. **결론 문장만 낡았다.**

## 4. 남긴 것 — 정직하게

### DB 파일은 11.1GB 그대로다

2,510만 행을 지웠지만 파일 크기는 줄지 않았다. freelist **132만 페이지(≈5.2GB)** 가 재사용
대기 상태다. `incremental_vacuum` 은 패스당 **1페이지**만 처리한다 — 이 DB 에 포인터맵이
없어서다(`auto_vacuum` 이 2 로 보고되지만 실질 동작하지 않는다).

디스크로 되돌리려면 전체 `VACUUM` 이 필요하고 그것은 **배타 락으로 API 를 장시간 내린다** —
방금 고친 장애와 같은 형태다. **유지보수 창의 일로 남긴다.**
그때까지 freelist 가 재사용되므로 **파일이 더 커지지는 않는다.**

### 폭주 원인은 수리하지 않았다

`KR/session_closed` 가 2026-08-14 하루에 2,528만 행 쌓인 기전은 조사하지 않았다.
`store.py:385-400` 에 `stale_seconds=300` 중복 억제가 있는데 이 경로가 그것을 타지 않는
것으로 보인다. 현재 15행/일이라 긴급하지 않지만 **재발 가능하고 리텐션은 증상만 막는다.**
