# WO-FCE-SAMPLE-RATE-01 — 표본이 안 쌓인다: 속도 격차 정면 대응

우선순위: P0 · 실사 기준: main @ `da44158`
선행: OBSERVATION-INTEGRITY-01, SAMPLE-VIABILITY-01, VALIDATION-VERDICT-01

## 0. 이 WO가 찾은 것

WO는 "표본 생성 속도가 기준에 미달한다"를 전제로 출발했다. Phase 3 실측이 **더 근본적인
문제**를 찾았다:

> **목표 30건은 게이트 축 2(성과 우위)가 요구하는 판정을 애초에 지탱하지 못한다.**

현재 방법(두 95% CI 비겹침)으로 30건에서 우위를 주장하려면 **승률 85%(40%p 우위)** 가
필요하다. 15%p 우위를 80% 검정력으로 잡으려면 **팔당 283건**이 필요하다.

`COMPLETION_DEFINITION.md` 의 30건과 `LIVE_TRADING_GATE.md` 축 2는 **서로 모순된다.**
그래서 실행 순서(Phase 1 → 3 → 2)가 옳았다 — 목표가 틀렸는데 용량을 늘리는 것은 순서가
틀린 것이다. **Phase 2 확대안은 제안까지만 하고 적용하지 않았다.**

## 1. Phase별 산출물

### Phase 1 — 속도 격차 정량화

`app/validation/sample_rate.py` — 진입률·청산 전환율에 더해 **보유기간과 동시 보유 최대치**를
잰다. 진입만 봐서는 오진한다: 슬롯이 유한하므로 처리량은 `C × D / H` 에 갇힌다.

동시 보유를 설정값이 아니라 **원장에서** 재는 이유는, 설정 한도가 실제로 다 쓰이고 있는지가
바로 이 WO의 질문이기 때문이다. 한도가 8인데 관측 최대가 2라면 한도를 올려도 소용없다.

부족분 역산은 세 축(진입률 배수 / 추가 유효일 / 보유기간 단축률)을 **대안**으로 낸다.

정본: [`docs/validation/SAMPLE_RATE.md`](validation/SAMPLE_RATE.md)

### Phase 3 — 필요 표본 재산정 (핵심)

`backend/scripts/required_sample_analysis.py` — 몬테카를로 3,000 시행, 시드 고정, 결정론.

| 방법 | 필요 N (팔당) | 현재 대비 | 오판율 |
|---|---|---|---|
| M0 현재 (CI 비겹침) | 283 | 1.00배 | 0.3% |
| M1 2표본 비율검정 (α=0.05) | 137 | 0.48배 | 5.6% |
| M2 페어드 ρ=0.5 | 86 | 0.30배 | 4.7% |
| M2 페어드 ρ=0.7 | 64 | 0.23배 | 5.7% |
| M3 순차검정 (Pocock 보정) | 211 | 0.75배 | 2.5% |
| M4 효과크기 | 174 | 0.61배 | 2.8% |

- **현재 비교는 독립이다** — 페어드가 아니다(`paper_scoreboard`, `edge_verdict` 모두).
  페어링 전환은 "같은 날·같은 심볼" 겹침이 실제로 있어야 가능하며, 확인 쿼리를 문서에 넣었다.
- **M0는 α=5% 검정이 아니다.** 실효 유의수준이 약 0.3%다 — 엄격해서 좋은 게 아니라
  얼마나 엄격한지 아무도 모르는 채로 엄격하다.
- M0 → M1 전환은 오판율을 0.3%→5.6%로 **올린다.** 효율 개선이 아니라 확신 수준 변경이므로
  **권고하지 않고 선택지로만 낸다.**

정본: [`docs/validation/REQUIRED_SAMPLE.md`](validation/REQUIRED_SAMPLE.md)

### Phase 2 — 기회 표면 확대

허용(용량)/금지(품질) 축을 문서로 갈랐고 TPS 검산 절차와 "한 번에 하나씩" 원장 표를 만들었다.
**적용은 0건** — Phase 3에서 목표 N 자체가 재검토 대상이 됐으므로 목표가 정해지기 전에
용량을 늘리는 것은 순서가 틀렸다. 원장 표가 비어 있는 것이 그 증거다.

### Phase 4 — 폴리 택일

**택일 규칙을 실측 전에 고정**했다(그대로 진행 / 유니버스 확대 / 트랙 유보). 실측은 호스트
1회 실행이 필요하다. 기존 보유 8건은 미청산 유지 — 소급 청산은 엔진 판단이 아닌 결과를
성과로 계산하게 만든다. **만기 상한을 늘려 "정산 가능"을 만드는 것은 금지**다.

### Phase 5 — 결정 대기 상시 노출

`app/validation/pending_decisions.py` — 진단 API·`/validation` 화면·주간 리포트에 상시 노출.
코드로 확인 가능한 항목(게이트 서명, 절전 보호)은 자동으로 닫히고, 나머지는 사람이 문서를
고칠 때 닫힌다. **"아마 했을 것"으로 닫지 않는다.**

> WO 문안의 미결 4번째 항목(2026-07-17 제헌절)은 **이미 닫혔다** —
> VALIDATION-VERDICT-01 Phase 5에서 재지정 확정을 확인해 `KR_CONFIRMED` 로 옮겼다.
> 다시 "결정 대기"로 올리지 않는다.

## 2. 이 세션이 산출할 수 없었던 것

운영 SQLite는 사용자 호스트에 있다. 아래는 장치까지만 만들었다.

| 항목 | 산출 명령 |
|---|---|
| 4트랙 격차 표 (진입률·전환율·보유기간·부족분 역산) | `curl -s localhost:8875/api/system/paper/diagnosis \| python3 -m json.tool \| grep -A 60 sample_rate_gap` |
| 폴리 신규 진입·정산 가능 건수 | `cd backend && python3 scripts/sample_viability_report.py ~/fomo_control_engine.db` |
| 페어링 가능 여부 (같은 날·같은 심볼 겹침) | `REQUIRED_SAMPLE.md` §3 SQL |
| 확대 전후 진입률 대조 | 확대 적용 후에만 가능 (현재 적용 0건) |

Phase 3 재산정은 **실측 데이터가 필요 없어 이 세션에서 완결됐다.** 시뮬레이션이므로
누구든 같은 시드로 재현할 수 있다.
